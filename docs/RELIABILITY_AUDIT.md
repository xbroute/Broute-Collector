# بررسی پایداری Broute Collector

تاریخ بررسی: ۲۰۲۶-۰۹-۳۰. مبنای کد: commit
`aba15f4ea201635bc77ce50ba0ccc452849e2f2a` روی `main`.

دامنه بررسی شامل کل خط لوله جمع‌آوری، پارسرها، شناسه اتصال و حذف تکرار،
زمان‌بندی اعتبارسنجی، خروجی Subscription، ناشر و کنترل بات تلگرام، state
رمزگذاری‌شده، Workflowها و تعامل سایت بود. تغییرات روی شاخه جدا انجام شدند.
منابع فعال، برند، داده‌های تولیدشده و state عملیاتی بات تغییر داده نشدند.

هویت کانفیگ‌های معمولی با queryهای استاندارد lowercase و fingerprint تلگرام با
path خالی حفظ شده است. بزرگی حروف نام query دیگر در شناسه اتصال از بین نمی‌رود. هویت
Shadowsocks طبق محتوای اتصال اصلاح می‌شود؛ generator سابقه را با canonical
connection matching منتقل می‌کند. URI با path واقعی در fingerprint تلگرام
متفاوت است. منابع جدید و تغییر ظاهری برند در این اصلاح‌ها وجود ندارد.

## روش آزمون

- مبنا: هر ۹۱ تست موجود پیش از تغییر پاس شد.
- مجموعهٔ گسترش‌یافتهٔ پایتون: ۲۳۶ تست، شامل سناریوهای قبلی و regressionهای جدید.
  API تلگرام، clock، DNS و socket در سناریوهای خطا mock شده‌اند؛ تست واحد پیام
  واقعی نمی‌فرستد. تست‌های قدیمی payload نیز دیگر برای CTA درخواست git واقعی
  انجام نمی‌دهند.
- پارسر VMess جداگانه با seed ثابت ۱۹ و ۱۰۰۰ ترکیب نوع/مقدار نامعمول اجرا شد؛
  تعداد exception مدیریت‌نشده پس از اصلاح صفر بود.
- compileall، بررسی syntax جاوااسکریپت و whitespace diff انجام شدند.
- ۲۷ بررسی مرورگر از داده مصنوعی شامل ۴۵۰ رکورد آنلاین و رکوردهای unknown، نامعتبر،
  حذف‌شده و منبع قطع‌شده استفاده می‌کند. درخواست خارجی بسته است. کپی دقیق URI،
  escaping نام، latency صفر، عبور از سقف ۲۰۰، فیلترها، clipboard fallback، خطای
  QR، فوکوس و نمای موبایل بررسی می‌شوند.
- اجرای آزمایشی واقعی روی ۲۹ منبع static فعال، در پوشه موقت و با بودجه ۲۰
  validation انجام شد: ۲۹ دریافت موفق، ۷۴۶ اتصال یکتا، ۲۰ validation تکمیل‌شده،
  صفر خطای validator و ۴۷۶ رکورد واجد شرایط online feed؛ زمان کل ۷۰٫۷۳ ثانیه.
  ۴۷۶ مقدار snapshot پس از انتقال سابقه است، نه تعداد اتصال تست‌شده در همین
  اجرا. منابع مدیریتی رمزگذاری‌شده در آزمون زنده محلی استفاده نشدند.

این اعداد گزارش یک اجرا هستند و تضمین عملکرد دائمی سرورهای عمومی نیستند.
تست مرورگر محلی از Chromium headless مستقل استفاده کرد؛ CI از مرورگر Playwright
نصب‌شده در runner استفاده می‌کند. آزمون انتشار واقعی تلگرام و تعویض Secrets
در آزمون‌های توسعه انجام نشده است؛ نتیجهٔ CI و ادغام از تاریخچهٔ GitHub قابل بررسی است.

## تکمیل مدیریت و تزریق خطا

پنل جدید با چهار نقش، بررسی همهٔ فرمان‌ها و callbackها، تأیید وابسته به actor/chat،
TTL سازگار با polling، جلوگیری از حذف آخرین مالک، audit رمزگذاری‌شده و migration
مدیران قبلی اضافه شد. راه‌اندازی دلخواه از گروه مهاجم بسته شد. ساعات ارسال،
سهمیهٔ محلی، فیلتر و مسدودی در ناشر و مرز ارسال اعمال می‌شوند. تاریخچهٔ صف تحت
کنترل پنل نوشته نمی‌شود. پشتیبان رمزگذاری‌شده، اعتبارسنجی پیش از بازیابی، OFF
بودن مقصدهای بازیابی‌شده، بازبینی دسترسی و retry خطای میانی پوشش داده شده‌اند.

در بررسی لاگ نسخهٔ مستقر، نبود فایل مقصدها در شاخهٔ state اولیه مشخص شد؛
نبود تأییدشده در tree تازه، مقصد خالی محسوب می‌شود. خطای fetch یا خواندن فایل
موجود همچنان توقف امن دارد. خطای ناشر دیگر با success کلی Workflow پنهان نمی‌شود.

دفتر ثبت ارسال، پیش از درخواست checkpoint می‌شود. timeout/5xx و crash میان
درخواست و ثبت موفقیت برای تصمیم اپراتور نگه داشته می‌شوند. تست تزریق خطا نشان
می‌دهد شکست checkpoint قصدِ ارسال، مانع درخواست Telegram می‌شود؛ پاسخ مبهم
خودکار retry نمی‌شود؛ startup با قصدِ ناتمام همان fingerprint را دوباره نمی‌فرستد.
429 و رد صریح API مسیر مستقل دارند. تصمیم `sent/retry` به attempt مشخص وابسته
است و یک‌بار اعمال می‌شود. exactly-once همچنان تضمین‌شدنی نیست؛ قرنطینهٔ محافظه‌کارانه
می‌تواند پیام ارسال‌نشده را نیز برای بررسی نگه دارد.

آزمون‌ها همچنین viewer/operator bypass، callback قدیمی، تأیید کاربر دیگر، expiry،
revocation، تنظیمات stale، سهمیه در نیمه‌شب ایران، بازهٔ شبانه، UTF-16 تلگرام،
Forum topic، URL نامعتبر، session پایدار، خطای تحویل پاسخ و حفظ offset را پوشش
می‌دهند. جزئیات استفاده در [TELEGRAM_ADMINISTRATION.md](TELEGRAM_ADMINISTRATION.md) است.

## محدودیت‌ها و قدم‌های بعدی

| اولویت | موضوع | پیشنهاد عملی و معیار پذیرش |
|---|---|---|
| بالا | TCP باز معادل VPN قابل استفاده نیست؛ UDP نیز بررسی نمی‌شود | runner جدا با Xray/sing-box برای handshake و یک درخواست آزمایشی محدود؛ افزودن validation_method و زمان اعتبار هر نتیجه؛ ابتدا مقایسه موازی با نتایج فعلی، سپس تغییر معیار feed |
| بالا | sendMessage شناسه idempotency ندارد | outbox، قرنطینه و تعیین تکلیف تأییدشده پیاده‌سازی شدند؛ exactly-once تضمین نمی‌شود. برای حجم تجاری، پایگاه دادهٔ تراکنشی و پایش attemptهای حل‌نشده لازم‌اند |
| متوسط | بازیابی چند فایل و چند شاخهٔ GitHub تراکنش مشترک ندارد | اعتبارسنجی کامل، master OFF، تأیید stale و retry امن اضافه شدند؛ تراکنش دیتابیس قدم بعدی زیرساخت است |
| متوسط | GeoIP خارجی، HTTP و rate limit؛ کشور Unknown قبلی دوباره بررسی نمی‌شود | کش بر اساس IP با TTL، سقف درخواست و retry محدود برای Unknown؛ fallback به Unknown و امکان خاموش‌کردن کامل lookup |
| متوسط | resolver سیستم می‌تواند بیش از بودجه TCP زمان بگیرد | DNS resolver با timeout صریح و کش کوتاه؛ تست DNS کند. timeout socket بودجه اتصال را محدود می‌کند، نه زمان قطعی getaddrinfo سیستم را |
| متوسط | GitHub cron و fetchهای git کنترل، تأخیر و هزینه دارند | اندازه‌گیری dispatch-to-control و fetch latency؛ استفاده از cache validator یا API با ETag بدون حذف بررسی OFF پیش از ارسال؛ worker دائمی فقط پس از تصمیم درباره میزبان |
| متوسط | TLS badge اعتماد، بررسی certificate یا رمزنگاری پروتکل‌های دیگر را بیان نمی‌کند | فیلدهای جدا برای قابلیت TLS، روش رمزنگاری و نتیجه handshake؛ حفظ توضیح فعلی در UI تا زمان ایجاد داده قابل اثبات |
| پایین | QR و فونت به CDN وابسته‌اند | نسخه محلیِ مجاز همراه مجوز و checksum؛ تست حالت offline و صحت decode QR پیش از حذف CDN |

سورس‌های static یک allowlist تحت کنترل مالک مخزن هستند؛ fetch آن‌ها مانند
منابع مدیریتی pinning همه redirectها را ندارد. برای منابع اضافه‌شونده از بات،
کنترل DNS، redirect، حجم و محتوای subscription موجود حفظ شده است. گسترش این
سیاست به تمام allowlist باید با تست سازگاری میزبان‌های فعلی انجام شود.
